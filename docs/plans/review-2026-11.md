## 1. Branch protection on `master`

## 2. Terraform state file modes

**Why.** `terraform/vault/terraform.tfstate*` and `terraform/oci/terraform.tfstate*` are mode 666 and hold secrets (Vault policies and tokens, the OCI setup). The home directory is 750, so today only group `pimaster` and root can reach them. The fix is defense in depth. The files were created 666 before the move to Oracle; OpenTofu keeps an existing file's mode when it writes it again.

- [ ] `chmod 600 ~/pi-cluster/terraform/{vault,oci}/terraform.tfstate*`
- [ ] Look for other world-writable files: `find ~ -xdev -type f -perm -o+w -not -path '*/.vscode-server/*' -not -path '*/.cache/*'`, and fix any that turn up.
- [ ] After the next `make configure-vault`, check the mode is still 600. New files get 644 (the runner's umask is 0022), so nothing else needs to change.

## 3. Control host backup

**Why.** pimaster holds what isn't in Git: `~/.secrets` (Vault unseal keys and root token, the restic offsite password, the OCI API key, WireGuard keys, IONOS credentials), `~/.certbot`, `~/.ssh` and the Vault and OCI state. Nothing copies them anywhere. pimaster and the offsite VM are in one Oracle Always Free account, so losing that account loses the control host and the offsite copy together. The offsite copy is also unreadable without the restic password, which lives only on pimaster.

Design: a daily restic backup from pimaster to a new bucket on RustFS at home. The nightly offsite copy then takes it to the Oracle VM as well, since it already copies `/storage/rustfs`. The keys needed to read any of it are also kept in a password manager, outside both places.

Steps:

- [ ] **Bucket and user.** Add a `control-host` bucket, a `control-host` user and a policy limited to that bucket to `terraform/minio/resources/`, with the S3 secret written to Vault (`secret/s3/control-host`) the way the other users' are. Merge it. The Deploy workflow plans it and asks for `terraform-apply` approval: the first real apply through CD.
- [ ] **Script.** `scripts/control-host-backup.sh` runs restic from the `restic/restic` image (pinned, with a `# renovate:` comment like `scripts/render-diagrams.sh`):
  - It backs up `~/.secrets`, `~/.certbot`, `~/.ssh`, `~/.kube`, `~/tfstate-backup` and `~/pi-cluster/terraform/{vault,oci}/terraform.tfstate*`. Not `~/actions-runner`: a lost runner is registered again.
  - Retention matches offsite: `--keep-daily 7 --keep-weekly 4 --keep-monthly 6`, then `prune`.
  - It doesn't read Vault at run time: a backup has to work while Vault is down. The S3 credentials sit in `~/.secrets/restic-control-host.env` (mode 600), written once from Vault by a small task in `configure_minio.yml`, or by hand.
  - The repository password is a new `~/.secrets/restic-control-host.password`.
- [ ] **Timer.** A systemd service and timer in the repo (`User=pimaster`, daily at 03:30), installed with `sudo install` the way the runner guard is. Lingering stays off.
- [ ] **Offsite.** Check that `offsite_restic_paths` in `group_vars/all/offsite.yml` doesn't exclude the new bucket. Today it excludes only `k3s-loki`.
- [ ] **Keys outside both places**, in your password manager:
  - `restic-control-host.password`
  - `restic-offsite.password`
  - a copy of `vault.env` (the unseal keys and root token)
  - the break-glass SSH key and its passphrase

  Without these, both copies are ciphertext.
- [ ] **Restore drill.** Restore the latest snapshot into a scratch directory, `diff -r` it against the live files, and record the date and time taken in [backup and recovery](../backup-and-recovery.md).
- [ ] **Docs.** A Backup section in [control host](../control-host.md): what is backed up, where, how to restore onto a new host. A line in the quick start: optional, but recommended.
- [ ] **Alerting** (after 3.0 phase 5): `OnFailure=` on the service sends a Telegram message. Until then, check `systemctl list-timers` and `restic snapshots` weekly.

Done when the timer has run for a week, the drill is recorded, and the four keys are in the password manager.

## 5. Memory requests

**Why.** 78 of 114 running containers (2026-11-11) have no memory request. The largest groups are longhorn-system (20), kube-system (15), kube-prom-stack (9), loki (7), cattle-fleet-system (5), fluent (5), cert-manager (4) and external-secrets (3). With 4 GB nodes, the scheduler places pods without knowing the real load. `kubectl top` shows the nodes at 89–118% of allocatable memory.

Method, for each namespace group:

- [ ] Measure the peak working set over 7 days in Grafana: `max by (namespace, pod, container) (max_over_time(container_memory_working_set_bytes{container!="",container!="POD"}[7d]))`.
- [ ] Set the request to peak × 1.1, rounded up, through the chart's values in `overlays/prod/values.yaml`. Set no new memory limits: on 4 GB nodes an OOM kill at a peak hurts more than the overcommit. Keep the limits charts already set.
- [ ] Before merging, add up the requests per node (`kubectl describe node <n>`, "Allocated resources") with the new values. If a node would go over 100% of allocatable, pods stay Pending at their next reschedule: lower the request or move the pod.
- [ ] After merging, check that nothing is Pending and no pod restarted with OOMKilled.

Order, cheapest restart first:

- [ ] loki, fluent, external-secrets, cert-manager
- [ ] kube-prom-stack
- [ ] longhorn-system. The manager and CSI pods restart one node at a time. Instance managers aren't touched; Longhorn sizes them itself.
- [ ] kube-system:
  - coredns, metrics-server, kube-vip.
  - Cilium last, in a quiet window: every agent restarts, and node6 recompiles its endpoints. If node6's CPU makes that too expensive, leave Cilium out and say so.
- [ ] cattle-fleet-system is deployed by Rancher, not by this repo. Leave it unless the Rancher chart exposes Fleet's resources.

Done when every container this repo deploys has a memory request, and the exceptions (Rancher's Fleet, perhaps Cilium) are listed in [platform](../platform.md).
